12. Saving records, and forms shown with DIALOG

Two things arrived together in Foundation 6.0, and both are optional:

  • Fnd_Hook_IO_OnValidate, one place for code that must run just before a record is saved from an input form;
  • the DIALOG route, a setting that has Foundation show an input form with DIALOG in place of MODIFY RECORD and ADD RECORD, which gives the form a Form object.

A database that uses neither behaves as it did. This chapter says what each does, what changes when you turn the second one on, and how to find out where your own database stands before you decide. Chapter 6 covers building an input form; this one covers how it is opened and saved.

1. Code that runs before a save

Until now, code that had to run as a record was saved lived in each form method, under On Validate. Foundation now calls a host hook at that moment instead:

// Fnd_Hook_IO_OnValidate ($table_ptr; $formName_t)

Case of
	: ($table_ptr=(->[Invoices]))
		Case of
			: ($formName_t="Input")
				VALIDATE TRANSACTION
		End case
End case

That is the demo database's own: its invoice form works inside a transaction, and the hook validates it as the invoice is saved.

Foundation calls the hook before every save it makes from an input form, whichever way the form was opened: from On Validate when the form was opened with MODIFY RECORD or ADD RECORD, and directly when it was opened with DIALOG. It passes the form's table and the form's name. Both parameters are optional, so a project form of your own, which Foundation does not open, can call the hook itself; $table_ptr is then a nil pointer.

Four things to know:

  • The hook is optional. With no Fnd_Hook_IO_OnValidate in your database nothing is called, and a form that handles On Validate itself still does. The installer (chapter 3) creates the hook when you ask it to.
  • A form needs no On Validate branch of its own. A form that calls the hook from its own On Validate branch runs the hook twice, once from the form and once from Foundation.
  • The form still enables the event. When a form is opened with MODIFY RECORD, Foundation reaches the hook from On Validate, so the form must have that event turned on. It is one of the eight that chapter 6 asks every input form to enable.
  • The hook cannot refuse a save. By the time it runs the record is on its way. A check that may stop the save belongs in Fnd_Hook_IO_InputFormButton (chapter 6, section 6).

Moving the code you already have

Fnd_Dev_ConvertOnValidate does the move with you. Run it from the Execute Method dialog, interpreted. It finds each form method, object method and project method that handles On Validate without calling the hook, and steps through them one at a time. For each it shows the method as it is and, ready to edit, the hook and the method as they would be afterwards. Nothing is written until you choose Apply; the first Apply asks whether Foundation may change your database, and the originals are saved in Resources/Foundation/OnValidate-Backups.

Read each proposal. Code under On Validate is often short, but it can depend on variables set elsewhere in the form method, and only you know whether it still makes sense in a method called from outside the form.

2. Showing a form with DIALOG

A form opened by MODIFY RECORD has no Form object (chapter 6, section 2). Shown with DIALOG it has one, and so can use everything in 4D that is built on Form: bound expressions, form classes, data passed in and read back.

Nothing opens this way until you turn it on. Fnd_IO_UseDialog does that at three levels:

Fnd_IO_UseDialog(True)                        // every input form in the database
Fnd_IO_UseDialog(->[Contacts]; True)          // every input form of one table
Fnd_IO_UseDialog(->[Contacts]; "Input"; True) // one form

Pass False to turn a level off. A form's own setting wins over its table's, and a table's over the database's, so you can turn the route on everywhere and keep one table on MODIFY RECORD, or the reverse. The settings hold for every process: call the method once at start-up, in Fnd_Hook_Shell_Startup. A nil table pointer means a project form, and form names are not case-sensitive.

To ask which route a form takes:

$dialog_b:=Fnd_IO_UseDialog(->[Contacts]; "Input")

The demo database turns the route on for its Contacts table only, as an example to read.

3. What changes under DIALOG

MODIFY RECORD does a good deal that DIALOG does not. Foundation makes up the difference for the form it supplies, Fnd_IO_InputForm, and anything that inherits from it:

With MODIFY RECORDWith DIALOG
The Form objectnonepresent; one object serves the whole visit, so it survives moving between records
On Validatefires when the record is acceptednever fires
Saving4D saves the recordFoundation saves it, calling Fnd_Hook_IO_OnValidate first
Cancel4D discards the changesFoundation unloads the record, which discards them
First, Previous, Next, Last4D's standard actionsthe standard actions do nothing; Foundation's buttons close the form and show it again on the next record, so On Load still runs for each record
The record4D loads itFoundation loads it before showing the form

Foundation puts three values on Form for you: Form.tableName, Form.processID and Form.listWindow, the window of the list the record was opened from, or 0.

Three consequences for your own forms:

  • Anything under On Validate stops running. Move it to the hook first (section 1). This is the one that matters.
  • A button of your own with a record-navigation standard action stops working. firstRecord, previousRecord, nextRecord, lastRecord and deleteRecord do nothing in a form shown with DIALOG. Foundation's own record buttons are taken care of.
  • A button of your own that accepts the form still saves: after the form closes, Foundation saves a record that is new or modified and calls the hook for it.

4. The check Foundation makes for you

Turning the route on for a table or the whole database is safe to try, because Foundation does not take your word for it form by form. It reads the code of each form, and a form whose code handles On Validate without calling Fnd_Hook_IO_OnValidate stays on MODIFY RECORD. So does a form it knows nothing about. Only a form it has cleared opens with DIALOG.

Naming a form yourself, with the three-parameter call, overrules that check: the form opens with DIALOG whatever its code does. Use that form of the call only for a form you have converted.

The reading needs your sources, so it happens in an interpreted database, the first time Foundation needs to know. The result is saved in Resources/Foundation/Fnd_IO_FormRoutes.json, and when it differs from what was saved before, Foundation reports the forms left on MODIFY RECORD and the project methods worth checking. It is saved only where Resources/Foundation already exists; the installer creates that folder. A compiled database cannot read its own sources, so it reads that file. Two things follow:

  • Ship the file. A compiled application without Resources/Foundation/Fnd_IO_FormRoutes.json has no cleared forms, and every form you turned on by table or database quietly stays on MODIFY RECORD.
  • Run interpreted once after changing forms, so the file is rewritten before you build.

A database that never calls Fnd_IO_UseDialog never reads its forms at all.

5. Finding out where you stand

Before turning anything on, Fnd_Dev_SanityCheck tells you what would happen. It reads the sources on disk, so run it interpreted; it shows nothing on screen and returns an object:

$result_o:=Fnd_Dev_SanityCheck
// $result_o.counts.error, .warning, .note
// $result_o.findings: collection of {check; severity; where; message}

Among its checks, the ones that bear on this chapter report:

  • a table form that handles On Validate without calling the hook, and so would stay on MODIFY RECORD;
  • a form or object method that calls the hook from its own On Validate handling, and so would run it twice;
  • an object of yours with a record-navigation standard action, as a warning when the route is on for that form and a note when it is not.

The same sweep also checks each form file against 4D's form format and the events a form enables against the events its methods test; neither has anything to do with DIALOG, and both are worth having. The compile-check watcher (chapter 11) runs the same sweep when its request file names the action sanity.

6. Should you turn it on?

There is no need to. MODIFY RECORD remains the default, and an existing database loses nothing by leaving the route off.

Turn it on for a form when you want what Form gives you, and that form's save-time code is short enough to move with confidence. A table at a time is the sensible pace: convert its form, run the sanity check, turn the route on for that table, and use it.

Leave it off, for now, for a form whose save does a great deal: one that validates several related records, or relies on state built up across the form method. Moving that code out of the form is a piece of work in its own right, and nothing obliges you to do it.

What has been tried, as of 6.0, in the demo database on 4D 20 LTS, interpreted and compiled: saving, cancelling, the close box, new records, adding several records in a row, and moving between records. What has not been tried: the route on 4D 21, and mandatory fields and entry filters, which MODIFY RECORD enforces on accept. If your form depends on either of those, test it before relying on it.

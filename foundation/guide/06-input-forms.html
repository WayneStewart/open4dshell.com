Building a Foundation input form

How a host database gives one of its tables a data-entry form that Foundation drives: navigation between records, the Save and Cancel paths, record I/O and window handling all come from Fnd_IO_InputForm; you draw the fields and wire the related tables. The worked example is the demo database, Foundation Product Sales: an Invoices record (table 6) with its Contacts parent (table 4) and its LineItems children (table 7).

Written for a developer or an AI agent building such forms from a catalog. Everything an agent cannot see at compile time is marked not checked by the compiler.

1. Where the form lives, and why

Input forms are table forms: Project/Sources/TableForms/<n>/Input/, where <n> is the table number from catalog.4DCatalog (<table name="Invoices" … id="6">), not its name. Foundation opens records with DIALOG, MODIFY RECORD or MODIFY SELECTION on the table, and each of those takes a form of that table, named Input unless Fnd_IO_InputFormName sets another. Fnd_IO_InputForm, which supplies the buttons and record handling, is a project form under Forms/; your table form inherits from it. This is deliberate, not legacy drift.

FileHoldsBound by
TableForms/6/Input/form.4DFormthe form, JSON—
TableForms/6/Input/method.4dmthe form method, a thin shell"method": "method.4dm" at the top level of form.4DForm
TableForms/6/Input/ObjectMethods/<objectName>.4dmone per object that has code"method": "ObjectMethods/<objectName>.4dm" on that object

A method file is bound only by its method property. Without it the file is compiled and never run: a form with no form-level method opens with no buttons, no title and empty lists, and the compile check is clean. An object also receives only the events listed in its own events array (sections 4 and 5 give them).

files and templates written for 4D in general often say otherwise. For Foundation input forms, this chapter wins on these points:

  • input forms are new table forms, not project forms under Forms/;
  • the form's own record is read classically, related data with ORDA (section 2);
  • one process object holds the form's shared state (section 2), so the form has no other process or interprocess variables;
  • the form subscribes to all eight events, handled or not (section 3);
  • objects are named Table-Field, not prefix_name (section 3).

2. Classic for the form's own record, ORDA for everything else

A form opened by MODIFY SELECTION or MODIFY RECORD has no Form object and no entity. (Chapter 12 describes the optional DIALOG route, which gives an input form a Form object; what follows is the default.) The current record is what exists, so the form reads its own record classically ([Invoices]InvoiceNumber) and reaches related data with ORDA (ds.LineItems.query(…)). That is the rule here, narrower than "never mix": classic for this record, ORDA for the rest. The record's parents count as part of this record: a parent display field is a classic field token loaded by RELATE ONE (section 4), while child lists and anything else queried are ORDA.

State the form and its objects share lives on a process object named for your project (FPS, ACME), created by an init method that Fnd_Hook_IO_DisplayRecord and Fnd_Hook_IO_DisplayTable both call, so it exists before any form opens; application-wide state goes in Storage.<Project>. Choose the name once, from the project's name or a prefix the project already uses, since every listbox data source will carry it. Property names derive mechanically from the table name: drop underscores, lower-case the first letter, capitalise what followed each underscore, then one of four suffixes that match the listbox properties they bind. For the LineItems table:

FPS.lineItemsSelection       // the entity selection
FPS.lineItemsCurrItem        // currentItemSource
FPS.lineItemsCurrItemPos     // currentItemPositionSource
FPS.lineItemsHighlighted     // selectedItemsSource

No abbreviations and no singularising: the table name as it is needs no registry.

Setting it up takes three pieces, shown for a project called ACME. First the init method, called on the first line inside the Your code markers of both Fnd_Hook_IO_DisplayRecord and Fnd_Hook_IO_DisplayTable (Foundation's own lines above the markers stay where they are):

// ACME_Init
var ACME : Object  // A process variable: one per process

If (ACME=Null)
	ACME:=New object
End if

Second, the typing for the Toolkit helpers' parameters. Whether the compiler insists depends on the project's Compilation path setting: where it requires all variables to be typed, it reports "has not been explicitly declared in the typing methods" for each parameter it cannot find in a method whose name starts with Compiler; on the default setting it infers them and says nothing. The entries do no harm either way, so add one for each helper you copy that has parameters or a result, and no others. Gen_IO_DisplayParent is needed only where a parent field is clickable (section 4):

// Compiler_ACME
If (False)  // Read by the compiler, never run
	C_POINTER(Gen_GetFieldPtr_Name; $0; $1)
	C_POINTER(Gen_IO_DisplayParent; $1; $2)  // only if you copied it
	C_TEXT(Gen_WindowTitle; $0)
	C_TEXT(Gen_FormCheck; $1; $2; $3)
End if

Third, register the new methods, with every helper you copied, in Project/Sources/folders.json; the IDE's method folders come from that file:

"ACME": {
	"methods": ["ACME_Init", "Compiler_ACME", "Gen_FormCheck", "Gen_GetFieldPtr_Name", "Gen_WindowTitle"]
}

(add Gen_IO_DisplayParent to the list when you copy it).

3. Making one

The installer (chapter 3) puts Forms/Fnd_IO_InputTemplate in your project, beside Fnd_IO_InputForm which every input form inherits. It is a copy-from template whose help object lists these same steps; copy its objects into the new form, then delete the help object. Several things in it are historical:

  • the "window size 450 x 300" step: use automatic sizing with the margins below;
  • its margins (19 and 20) and its 16-pixel fields;
  • its placeholder bindings to [Products:5]Description:4, which belong to no table of yours: rebind every object you keep from your own catalog;
  • the step "Associate and Activate the Fnd_Shell, then select <None>", a setting from older 4D: skip it; Foundation builds its menus at run time and the inherited form needs nothing else;
  • the LargeField and LargeLabel classes, which no shipped style sheet defines: leave them out;
  • page 0 written as null, which is right only for a tabless form.
  • Read the catalog first. Take the table's fields in order with their ids and types, its N-to-1 relations (they become parent fields) and its 1-to-N relations (they become child listboxes). Every dataSource token is [Table:tableId]Field:fieldId; a wrong id binds silently to the wrong thing, so derive them, never guess. The ORDA names of a relation are on its <relation> element: name_Nto1 is the name used from the child (name_Nto1="invoice" gives ds.LineItems.query("invoice.Invoice_ID = :1"; …) and the column This.invoice.…), name_1toN the name used from the parent. A parent's display field is the field a user knows the record by: its Name field if it has one, otherwise the first text field that identifies it (Company, company_name), or its picture field when it holds nothing else.
  • Write form.4DForm. Four settings are load-bearing: "method": "method.4dm"; "inheritedForm": "Fnd_IO_InputForm"; all eight events (onLoad, onValidate, onActivate, onCloseBox, onOutsideCall, onClick, onDataChange, onResize); and formSizeAnchor naming the object whose bottom-right corner is furthest down and right (usually the tab control, or the last field on a tabless form), with "rightMargin": 20 and "bottomMargin": 60. The form's width is then the anchor's right edge plus 20 and its height the anchor's bottom edge plus 60. The 60 makes room for the inherited Save, Cancel and navigation buttons: in the editor they sit at the top left under a "hide this" picture, and Fnd_IO_InputFormMethod moves them to the bottom when the form loads. pages[0] is the background layer drawn on every page, not a page: a form whose only entry is pages[0] crashes 4D on open with no message, and a compile check cannot see it. Every form needs pages[1]. On a tabless form, put everything on pages[1] and leave pages[0] empty. On a tabbed form, the record's fields, parent fields and the tab control go on pages[0], and each child listbox gets a page of its own from pages[1] (section 5).
  • Lay out the record's own fields, one label and one field per row. Name objects Table-Field with a hyphen (Invoices-InvoiceNumber, Label-InvoiceNumber); the template's Fnd_IO_Field1…n names are a starting point, nothing depends on them. Hyphens are fine; full stops are not (object notation reads them as property access). Labels use 4D's reference syntax (<?3>: is field 3 of the current table, <?[4]>: is table 4's name) so they follow renames. A single-line input at the form font is 17 pixels high, not the 21 the editor draws. ID is shown, non-enterable: these are developer forms. An enterable field is sunken, stroke #000000, fill #FFFFFF, and needs no events of its own: Foundation does not use On Data Change, so add "events": ["onDataChange"] only to a field whose change the form method handles. The template's fields carry it; it does no harm, but nothing reads it.
  • A parent field per foreign key (section 4), clickable only if the parent table has an input form of its own.
  • A tab control and child listboxes, every column non-enterable (section 5).
  • The form method (below), and an object method only on a parent field or listbox that opens another table's input form (sections 4 and 5). Where the target table has no input form the object is inert, with no method and no events; a form whose related tables have none has no ObjectMethods/ folder at all.
  • Check the JSON, compile, then open it (section 7). The compiler validates code, never form JSON: a form with no method property, or a tab that changes nothing, compiles clean. Read the saved JSON back, or run Gen_FormCheck from Toolkit/, before reporting, and say which checks were left for someone to click through.

Both click-throughs in the example need their target's input form (section 4). Contacts has one in FPS; LineItems does not, so in FPS itself the listbox would carry no method and no events. An inert object drops events and method; an inert listbox keeps everything else shown above, and an inert parent field also takes the inert style of section 4:

"Contacts-Company": {"type": "input", "dataSource": "[Contacts:4]Company:4", "left": 128, "top": 48, "width": 280, "height": 17,
	"enterable": false, "focusable": false, "borderStyle": "sunken", "stroke": "#696969", "fill": "transparent"}

Two more column types: a date takes "dataSourceTypeHint": "date" with "dateFormat": "systemShort", and a Boolean takes "dataSourceTypeHint": "boolean" with "controlType": "checkbox", or it shows as text. A picture field, such as a parent that is only a photo, is an input with "dataSourceTypeHint": "picture" and "pictureFormat": "proportionalCenter", not a picture object, which has no data source.

The form method

var $formEvent_o : Object

$formEvent_o:=FORM Event

Case of
	: ($formEvent_o.code=On Load)
		SET WINDOW TITLE(Gen_WindowTitle)
		Fnd_Menu_Window_Add  // Update the Window menu
		RELATE ONE([Invoices]Contact_ID)  // One per foreign key: loads the parent display field
		FPS.lineItemsSelection:=ds.LineItems.query("invoice.Invoice_ID = :1"; [Invoices]Invoice_ID).orderBy("LineItem_ID asc")
End case

Fnd_IO_InputFormMethod

Declare, then assign: initialising on the var line is a syntax error before 4D 21. Fnd_IO_InputFormMethod must be called; where it sits does not matter, the title included: it sets a title only when the window has none, or has one it set itself, so the form method's SET WINDOW TITLE stands either way. A Case of on the event code is right here because the form subscribes to eight events.

On Load runs for every record. Foundation's navigation buttons display each record afresh, so On Load runs again on every move, and the parents and child lists loaded there follow the record. Load every child selection at On Load. The query and its orderBy run then, once per record; the listbox only draws the rows in view, so a long child list costs its query, not its display. Per-table setup that must happen before the window opens (window type, title, nav buttons) goes in the Case of on the table pointer in Fnd_Hook_IO_DisplayRecord, as FPS does for [CompanyInfo] and [Invoices].

Window titles come from Gen_WindowTitle (in Toolkit/), never from a hand-built string: it reads the current table and record, says "Invoices: New Record" for a new one, and clips long titles. Copy it and Gen_GetFieldPtr_Name into your project. The title uses the table's Name field, or its first text field when it has none; where that is not enough (a first name alone, say), add a branch to the Case of in Gen_WindowTitle following the commented [Invoices] example:

: ($table_ptr=(->[Contacts]))
	$windowTitle_t:=$windowTitle_t+": "+[Contacts]FirstName+" "+[Contacts]LastName

The form method's SET WINDOW TITLE sets the title once the form has loaded, and again for each record. If it must be right before the window first appears, also call Fnd_Wnd_Title(Gen_WindowTitle) for that table in Fnd_Hook_IO_DisplayRecord, with the other before-the-window setup.

4. Navigating up: the parent as a display field

Do not show the raw foreign key. Bind the field to the parent's display field, [Contacts:4]Company:4 rather than [Invoices:6]Contact_ID:2, with enterable: false and focusable: false. The form method's RELATE ONE loads it. The object takes "events": ["onClick"] and "method": "ObjectMethods/<objectName>.4dm", and the object method is one line:

Gen_IO_DisplayParent(->[Contacts]; ->[Invoices]Contact_ID)

A parent with no text worth showing, such as a table holding only a picture, is handled the same way: bind the parent's picture field itself, in an input object (section 3 gives its two picture properties), with the same RELATE ONE, events and one-line method.

A click-through needs somewhere to land. The wrapper opens the parent table's own input form. If that table has none (no TableForms/<n>/Input/), the click opens nothing: Foundation shows a bug alert naming the table and the form it looked for (a 4D error before Foundation 6.0). Build the parent's input form first, or leave the click-through out: no method, no events, and the inert style below, so the field shows the parent's name and nothing more. The same holds for the child rows in section 5.

Call the wrapper, never Fnd_IO_DisplayRecord directly. Fnd_IO_DisplayRecord unloads the related record on return, so a direct call leaves the field blank the moment the user clicks it: the parent window opens correctly and the field empties behind it. The wrapper (in Toolkit/) is RELATE ONE, display, RELATE ONE again, and exists because the two statements are only correct together.

One click or two buttons. A field carrying the method is enough where the parent is set elsewhere and only ever looked at. Where the user must also change or create the parent, the field carries no method and Display and Choose buttons sit beside it: one handler cannot serve three intentions. FPS's Invoices form shows the full set as View, Clear, Select and New Contact buttons, with SelectContact as the chooser form. The chooser is the host's own: the Toolkit supplies no generic one. Where nothing yet needs changing the parent, build the one-click field and leave choosing out.

Read-only fields must not look alike. Inert (ID, a total): sunken, stroke #696969, fill transparent. Clickable (a parent field with no buttons): raised, stroke #000000. Raised is a button affordance, so raised only where the object has a method.

5. Navigating down: child listboxes on tabs

More than one child table goes behind a tab control on page 0. Page 0 objects appear on every page, so the record's own fields stay visible while the tabs change the child list; a fourth child needs no redesign. The listbox and its tab control both take sizingX: grow, sizingY: grow, or the listbox leaves a gap on resize.

A tab control does something only if it is told to. A click changes the tab's own value and nothing else, with no error, unless one of these is set:

  • One listbox per page (the pattern this chapter shows): the tab has "action": "gotoPage", and each child's listbox is on its own page from page 1. Tab n shows page n, so the labels follow the page order.
  • One listbox, refilled: the tab has a method of its own, with "events": ["onClick"], that empties the single listbox and loads the chosen child into it. Fewer objects and no pages to keep in step; the method does the work the pages do in the first pattern.

For the first pattern:

"Invoices-Tabs": {
	"type": "tab",
	"left": 20, "top": 200, "width": 560, "height": 250,
	"sizingX": "grow", "sizingY": "grow",
	"action": "gotoPage",
	"labels": ["Line items", "Payments"]
}

(Payments stands for a second child table; FPS has only one.) Anything that draws a chosen page directly, such as the Form editor, shows every page correctly whether or not the tab works; only clicking the tab in the open form tests it.

Columns traverse the wired relations and show what the user reads: This.product.ProductName, not This.Product_ID. Where a column needs composing, put an exposed Function on the entity class and bind This.lineText(); never assemble the string in the form and never parse one back. Show every field of the child except its own key and the foreign key to this form's table, with each other foreign key replaced by the related record's display field.

Names. Every object name in a form must be unique, and 4D counts list box columns and headers as objects too. Name the tab <Table>-Tabs, each listbox <ChildTable>-List, each column <ChildTable>-<field or relation> (LineItems-product) and each header Header-<column name>. Prefixing the child table keeps two lists that both show a project from colliding.

Header sorting is safe to leave on: a list box bound to an entity selection writes the sorted selection back to its dataSource property, so the position the double-click handler reads still matches the selection it uses.

Non-enterable is not cosmetic. A listbox bound to an entity selection writes through: an enterable This.product.ProductName would rename a Product from the Invoices form.

Bind currentItemSource, currentItemPositionSource and selectedItemsSource to the process-object properties of section 2; the double-click handler needs the position. The listbox takes "events": ["onDoubleClick"] and a method path, so its method runs on that event alone and needs no event test. The position counts from 1 and is 0 when no row is selected, as after a double-click below the last row:

If (FPS.lineItemsCurrItemPos>0)
	USE ENTITY SELECTION(FPS.lineItemsSelection)
	GOTO SELECTED RECORD([LineItems]; FPS.lineItemsCurrItemPos)
	Fnd_IO_DisplayRecord(->[LineItems])
End if

Three lines, and the two worlds meet once. Fnd_IO_DisplayRecord is right here: a child row has no parent display field to restore. It opens the child table's input form, so give the listbox this handler only when that table has one (section 4); otherwise list the rows with no method and no events.

The self-join hazard. A child listbox on the same table as the form gets no double-click handler: USE ENTITY SELECTION plus GOTO SELECTED RECORD would move the current record of the table the open form is bound to and discard the user's unsaved keystrokes. List the rows and leave navigation out.

6. Validation before saving

Pre-save checks go in Fnd_Hook_IO_InputFormButton. The Save button belongs to the inherited form, so there is no object method of yours to hold them. The hook receives the button name in lower case ("save", "cancel", "first", …) and returns $allow_b, already set to True above the Your code marker; set it to False to stop the default action. Branch on Fnd_Gen_CurrentTable; on failure alert, put the cursor in the offending field by the object name the Table-Field convention makes predictable, and set $allow_b:=False. By name, GOTO OBJECT needs the star:

If (($button_t="save") && (Fnd_Gen_CurrentTable=(->[Contacts])) && ([Contacts]LastName=""))
	Fnd_Dlg_Alert("A contact needs a last name.")
	GOTO OBJECT(*; "Contacts-LastName")
	$allow_b:=False
End if

A table with no rules needs nothing here: $allow_b stays True.

Watch the empty test on a text field: If ([Contacts]EmailAddress=!00-00-00!) compiles cleanly and throws "A function was expected" at runtime. The test is ="". This hook sees the UI only; a rule that must hold however a record is written belongs where every path passes.

Code that must run as the record is saved, as opposed to a check that may stop the save, goes in Fnd_Hook_IO_OnValidate (chapter 12). The form method needs no On Validate branch for it.

7. Checking a form, and building more than two

Check every form for the invariants a compile check cannot see, one form or fifty:

  • pages has at least two entries (section 3, step 2);
  • "method": "method.4dm" at the top level, and on every object with code a method path naming its file in ObjectMethods/ exactly, with that object's events listed;
  • each tab control has "action": "gotoPage" (and as many labels as pages after page 0) or a method of its own;
  • table and field ids match the catalog; relation names behind each column dataSource resolve; enterable: false on every column; eight events; inheritedForm set; no duplicate object names, columns and headers included; no orphan or missing object-method files;
  • every table a parent field or child list opens has an input form of its own. "Opens" means an object method calls Gen_IO_DisplayParent(->[…] or Fnd_IO_DisplayRecord(->[…]; an inert object opens nothing and passes.

Toolkit/Gen_FormCheck makes most of these checks for you. Run it through Foundation's compile-check watcher: {"action": "test", "method": "Gen_FormCheck", "parameters": ["Invoices", "Input"]}. It validates the form against the running 4D's own forms schema, which catches wrong value types and misspelt event names, then checks the list above. Each problem comes back as a failed assertion. The schema alone would pass a form with no method or a dead tab: it accepts any property, and requires none.

What only a person can check is what needs the form running: open a record whose parents and children have data, click each tab, click each parent field and come back, double-click a child row, move to the next record and see the lists follow, try Save with a required field empty, and resize the window.

Building many forms, generate them from a table-and-relation spec rather than by hand, and run the checks on every form the generator writes. Build the parents' and children's forms in the same pass, so every click-through has somewhere to land.

Two of these cost a 4D crash each before they were written down.

Files in Toolkit/

Gen_IO_DisplayParent.4dmthe parent display wrapper, for clickable parent fields only
Gen_WindowTitle.4dm, Gen_GetFieldPtr_Name.4dmwindow titles, with the per-table override commented
Gen_FormCheck.4dmthe static form check of section 7, run through the watcher

Gen_* are host-side project methods, not Foundation's API. Keep the names this chapter uses, or rename the prefix to your project's and change every call to match. Copy them into Project/Sources/Methods/, type their parameters and register them in folders.json (section 2). They call Foundation's shared Fnd_Shell_CommandWrapper and Fnd_Gen_PositionR, so they compile on 20 LTS and 21 alike.

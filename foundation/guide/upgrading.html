Foundation — upgrade notes for host databases

Written 2026-08-13 for the host developer, not the Foundation developer. The companion to README.md: that document says how a release is cut, this one says what a host must do to accept it.

One section per release, newest first. Every entry answers three things — what changed, what the host sees, what the host must do. An entry that needs no action still belongs here, because "we checked and it is safe" is worth recording once rather than re-deriving per site.

What counts as a breaking change

Foundation's contract with a host is every method carrying "shared":true, at the signature it had when the host was written. Not the methods a header comment calls public — hosts invoke Foundation by name at runtime through EXECUTE METHOD, stored method names and object-method wiring, and none of that is visible to any static reading of the component.

That distinction is not theoretical. In March 2026 the surface was narrowed from 697 to 451 shared methods on the strength of Access: header comments, shipped as Foundation 20 LTS, and broke host databases in the field. The rule since: a shared method is contract until runtime evidence from real hosts says otherwise, and removal is staged deprecation, never a flag flip.

So the categories below are ordered by what they cost a host:

  • Breaking — a call that compiles today stops working. The host must act.
  • Behavioural — the call still works and returns a different answer. The host must decide whether it cares.
  • Additive — new capability. Nothing to do.

From Foundation 5

For a host written against Foundation 5.x that is moving to 6.0. This section is the consolidated checklist, in the order a developer needs it; the beta sections below (newest first) remain the detailed record, with the reasoning and the exact method names. Where an item names a beta, read that section before acting.

1. Check the 4D version

The floor is 4D 20 LTS. 4D 19 is no longer supported. Foundation 6 is built for four targets from one commit, each shipped as a macOS DMG and a Windows ZIP: 20L (4D 20 LTS), 20R (4D 20 R, the final R), 21L (4D 21 LTS) and 21R (4D 21 R, the latest). Use the build that matches the 4D running your database.

2. Install the component

Replace Foundation.4dbase in the host's Components folder with the 6.0 build, then open the database interpreted.

3. Run the installer, and read what it offers

Foundation 6 asks before it adds anything to a host (beta.3, beta.4). In an interpreted host the first Foundation call that finds something missing opens the installer dialog; Fnd_Shell_Installer runs it at any time. It lists what it would add: the tables Fnd_Pref, Fnd_List and Fnd_SqNo, the Fnd_Hook_ and Fnd_Host_ methods, Compiler_Fnd_HookAndHost and, in a project-mode host, the five forms Foundation's windows are built on with their pictures under Resources/Foundation. Cancel adds nothing. A compiled host, a server and a remote client are never changed. Restart the database after choosing Install: the new tables and methods need it.

Back up the host, or commit it, before the first interpreted start-up. Anything of yours that already exists is left alone (a hook, a form, a picture), with one exception: a Foundation Fnd_Host_ or compiler method whose parameters are out of date is rewritten without asking, with the previous code kept below the new code as a comment, because the host would not compile otherwise.

Three further things a 5.x host will meet:

  • Tables made by Foundation 5 (Fnd_Pref, Fnd_List, Fnd_SqNo, and Fnd_Log and Fnd_Reg where used) may lack a primary key or journaling. The installer lists each under "Table upgrades" and, on Install, adds the key and enables journaling. Only a row with an empty or duplicate ID is changed (beta.4). Back up first.
  • The five forms (Fnd_Tlbr_Toolbar, Fnd_IO_InputForm, Fnd_IO_InputTemplate, Fnd_IO_OutputTemplate, Fnd_Out) are copied in only when missing; a copy already in the host is never replaced. Beta.4 describes how the installer marks a form superseded or edited and how to bring a superseded one up to date. A Foundation 5 copy matches none of the versions Foundation 6 has shipped, so the installer marks it edited and leaves it alone; compare it with the 6.0 form by hand. (A binary host is offered no forms at all.)
  • A new release announces itself once per machine, in an interpreted host only, with Review now, Skip this release and Never ask. End users never see it.

4. Typing and compiler methods

Foundation's own Compiler_Fnd_* methods travel with the component. A host that named one of the retired Compiler_Fnd_Data, Compiler_Fnd_Date, Compiler_Fnd_Ext or Compiler_Fnd_Wnd entries in its own typing was declaring Foundation's variables, which it never should have; remove the entry (beta.3). The host's own hooks and host methods are typed by Compiler_Fnd_HookAndHost, which the installer generates; keep it together with the methods it types.

Many modules have moved their state from process and interprocess variables to objects: Form.* for what a dialog displays, Fnd.<Module> per process and Storage.Fnd.<Module> shared. A host that read one of the old variables by name finds nothing (tables for Data and Text under the August 2026 modernisation below). The shared methods keep their names, parameters and behaviour, and the Fnd_Tlbr_SetHostVars and Fnd_Reg_SetHostVars contracts are unchanged. The input form the installer supplies no longer binds its eight buttons to variables; a form already in a host keeps its variables and works as before (beta.4).

5. Removed, renamed and replaced

Search the host for each of these. A call to something that no longer exists stops the host compiling.

  • Foundation's own licensing is gone (beta.1): Fnd_Gen_Reg_*, Fnd_Gen_RemoveActivationCode, their two forms and Resources/Fnd_License.xml. Remove any call or menu item for them. Fnd_Reg, which licenses your application, stays.
  • Ten shared methods removed (beta.3, with a replacement table there): Fnd_Gen_DummyMethod, Fnd_Nav_DummyMethod, Fnd_Pref_DummyMethod and Fnd_Rec_ModifyErrorHandler become Fnd_Gen_SilentError; Fnd_Out_ConfigureList becomes Fnd_Out_Default; Fnd_Out_ORDARelatedField, Fnd_Menu_LoadMenuTitles, Fnd_Reg_FeatureCodeIndex, Fnd_Msg_BlobToPicture and Fnd_Msg_PictureToBlob have no replacement.
  • Fnd_*_Init and Compiler_Fnd_* are no longer callable from a host (63 methods, beta.1). Delete any direct call; nothing relied on it. Public Fnd_<Module>_<Verb> methods kept their flags.
  • Three MD5 helpers removed (Fnd_Text_TextToMD5_Bits32Add, _Bits32Left, _Calc): use Fnd_Text_TextToMD5.
  • cs.fnd.wnd and cs.fnd.out are no longer published. Neither did anything; the unfinished window class is removed (rc.1).
  • German's language code is DE, not GR. Rename a host's own _GR lists _DE.
  • Interprocess and process variables of the Data, Text and Dlg modules are gone (tables in beta.1).

6. Behaviour a host could notice

  • Fnd_Data_FormatWebURL defaults to https, not http, and Fnd_Text_TextToBase64 no longer starts with a carriage return, so values stored by an earlier version will not match fresh output (beta.1).
  • Fnd_Dlg_SetIcon with any value other than the warning or stop icon resets the next alert to the Note icon (beta.1).
  • The Window menu lists windows, not processes; Fnd_Menu_Window_Add works on the current form window, and Close All reaches every closeable window of a process (beta.2). Check any call to Fnd_Menu_Window_Remove or Fnd_Wnd_SendCloseRequests that passes a number.
  • Preference names ignore case, as in Foundation 5 (beta.3).
  • The input form's Save and Cancel buttons take Foundation's localised title, replacing text typed on them (beta.3).
  • List windows: configuration is saved to Resources/Foundation/Fnd_Out/<Table>.json (the old folder is still read); Save in the Layout menu saves whatever layout is in force; a list refreshes when its window comes to the front; the Sort dialog sorts and remembers (beta.4).
  • Fnd_Log_CreateTable no longer overwrites the clipboard, and entries logged between Fnd_Log_Shutdown and the last log writer ending are dropped (beta.4).
  • Command names added with Fnd_List_AddItem are matched exactly (case-sensitive, no @); Fnd_Gen_Reset now also forgets the current table; Fnd_Loc_FixLabelWidths accepts object names as well as pointers.
  • A host that calls Fnd_Find_Engine with a custom search method must pass the search option as the new optional second parameter, or the method receives 0 (beta.4).
  • In an interpreted host that uses Fnd_Reg without a [Fnd_Reg] table, Fnd_Reg now offers to create it (beta.1).

7. What is new

Additions needing nothing from the host: the installer, the Fnd_Out search box and list fonts, Fnd_Dlg_SetClickToCopy, the window registry, Fnd_Art_VersionHistory with the tabbed About box, and the cs.fnd classes (text, date, pswd, pref, log). Beta.1 to beta.4 list each.

8. Fnd_Dict

Fnd_Dict is unchanged in 6.0 and still works. New code is better served by 4D's native objects and collections, but there is no need to move existing code off it.

9. Where the detail lives

The sections that follow are the full record: 6.0.0-beta.4 (installer, forms, list window), beta.3 (consent, removed methods), beta.2 (windows, search box) and beta.1 (licensing, Logging, shared-surface changes, Fnd_Text and Fnd_Data). The developer guide is Guide/, and the reference is at https://foundation.open4dshell.com/docs/.

6.0.0-rc.1 (release candidate, 27 November 2026)

The release candidate for 6.0.0. Run Fnd_Shell_Installer once in each host, interpreted, as for beta.4; nothing else needs doing in your database.

Breaking

No shared method was removed or had its parameters narrowed.

The toolbar's status variable Fnd_Tlbr_Info_t is gone. Foundation no longer declares it in the generated compiler method, and no longer generates the host method Fnd_Host_Tlbr_SetMessage, which assigned it and which Foundation has not called since beta.4. The rc.1 Fnd_Tlbr_Toolbar form does not use it: its status line has no variable, and the first button passes two parameters to Fnd_Tlbr_SetHostVars. What to check: a host still on an earlier copy of the form names the variable twice, in the status line Fnd_Tlbr_StatusText and in the method of Fnd_Tlbr_PictureButton1_i. The installer never rewrites a compiler method already in the host, so the old declaration stays where it is; but a host that deletes Compiler_Fnd_HookAndHost and lets the installer write it again stops compiling where variables must be declared. Replace the form (by hand, FND-108), or clear the status line's Variable or Expression and delete ; ->Fnd_Tlbr_Info_t from the button's method, or declare var Fnd_Tlbr_Info_t : Text in a Compiler method of your own. A copy of Fnd_Host_Tlbr_SetMessage already in the host is no longer needed and can be deleted.

Behavioural

Fnd_Host_GetIntegerValue needs no process variable. The generated method now reads the host's variable with Formula from string, so the process variable Fnd_Host_IntegerValue_t is gone from it and from the generated compiler method. What to check: nothing; a copy already in the host keeps working, and the installer does not replace it.

Command names added with Fnd_List_AddItem are matched exactly (FND-103). Case matters, and @ is no longer a wildcard. What to check: a host that adds a command under one spelling and refers to it under another must use one spelling.

Administration, Print, Special Functions and Open Table show their dialog after the hook runs. Foundation now displays the dialog, and re-enables the menus, once the hook has returned, so a hook need only add its commands. A hook that already shows the dialog itself keeps working, and the dialog is not shown twice. What to check: nothing is required. The templates the installer generates for these hooks no longer end with Foundation's action.

The Administration dialog is open to every user; the Password Editor in it is not. Without a hook, Foundation offers 4D's Password Editor only to the Designer, the Administrator and the Administration group, and the rest of its commands to everyone, where before a user outside those groups was refused the whole dialog. The generated hook does the same, and shows how to keep any other command for administrators. What to check: a host that relied on the dialog being closed to ordinary users should restrict its own commands in its hook. The generated Print hook carries the same administrators-only test, empty, ready for any report or editor that should not reach every user.

Fnd_Gen_Reset also forgets the current table, as it already forgot the rest of Foundation's per-process state.

Cmd-Backspace deletes in a list window (Ctrl-Backspace on Windows), as the toolbar's Delete button does. Before, it did nothing: 4D compares Char(Backspace) as equal to empty text, so the shortcut was matched to the first toolbar button without one. A host that registers its own toolbar shortcut with Char(Backspace) or by the name "Backspace" gets the same fix.

The toolbar's status line is set by object name (FND-103). Foundation now pushes the text to the form object Fnd_Tlbr_StatusText. Fnd_Tlbr_SetHostVars keeps its three parameters, the last two now optional; only the first (the picture variables) is used.

Fnd_Tlbr_Toolbar has two corrections. The hidden button Fnd_Tlbr_Shortcut_A had the shortcut key å (Option-A), so a toolbar button given the shortcut "A" never fired from the keyboard; the rc.1 copy uses a. And the status line Fnd_Tlbr_StatusText took the automatic text colour, white in the dark colour scheme, over the toolbar's light background, where it could not be read; it is now black, as the button labels are. The installer reports an unedited host copy as superseded. What to check: a host that uses the dark colour scheme, or gives a toolbar button the shortcut "A", should replace the form (by hand, FND-108), or make the same two edits in the form editor.

Fnd_Out alternates its rows in the colour scheme's own shade. The list box's alternate row colour was a fixed light blue (#F1F6FE), which glared in the dark colour scheme; it is now "Automatic Alternate". The installer reports an unedited host copy as superseded. What to check: nothing is required; a host that wants the change can replace the form (by hand, FND-108) or set the list box's Alternate Background Color to Automatic Alternate in the form editor. With the form automatic, Option-click (Alt-click) on a View Options colour swatch returns that colour to automatic, and the swatch shows the automatic shade rather than white. Foundation's own list boxes (the View Options palette, Manage Layouts, the Preferences editor) lose their fixed light blue the same way.

The alert icons are redrawn for dark mode. The note icon is now Foundation's cog in place of the 4D cube with a gear, and the warning and stop icons have proper transparency: their edges had been smoothed against white, which showed as a white rim in the dark colour scheme. The file names are unchanged, so a host that substitutes its own icon (through Fnd_Bttn_AlternativePicturePath) is unaffected.

More of Foundation's working state is kept in objects (FND-103): the toolbar, the Localization and Sequence Number editors, the Register dialog, the Choice List dialog, the list window's View Options and several smaller modules. Shared methods are unchanged and no host action is needed. Fnd_Dict is unchanged.

cs.fnd.out is no longer published, and neither is the unfinished window class that replaced cs.fnd.wnd in beta.1. Neither did anything. A host that referred to either must remove the reference.

cs.fnd.fnd is corrected. info answers through Fnd_Info (so "version" is the release version, not "5.4"), and the current table and form type are Foundation's own, through Fnd_Gen_CurrentTable and Fnd_Gen_CurrentFormType, rather than a private copy only the instance saw. Signatures are unchanged.

A missing input form gives a bug alert, not a 4D error. Fnd_IO_DisplayRecord checks that the table has the input form before it starts a process, and checks again after Fnd_Hook_IO_DisplayRecord, which may change the form name. When the form does not exist, nothing opens and Foundation shows a bug alert naming the table and form.

Edit on several selected records opens its windows in a cascade. In an Fnd_Out list, choosing Edit with more than one row selected used to open every record's window at the same saved position, one on top of the next; each now waits for the one before it, so they step down and across.

The list window's status line counts take thousands separators ("1,234 of 12,345").

French text reads properly. Fifteen translation files held their French strings in Latin-1 while Foundation reads them as UTF-8, so accented letters came through garbled. They are re-encoded; the text is unchanged.

Installing records the release. After Fnd_Shell_Installer has run, the next start-up no longer offers the new-release notice for the release just installed.

The About box's Licence tab also shows the third-party notice for the text comparison the installer uses to compare hook methods (Matthias Hertel's BSD licence).

Foundation calls Fnd_Hook_IO_OnValidate before it saves a record. The hook is new and optional: with no such method in your database nothing changes, and a form that handles On Validate itself still does. See Additive.

Fnd_IO_AddMultipleRecords(True) now reaches a record opened in its own window. The setting is per process, so set in Fnd_Hook_IO_DisplayTable it applied only where the record was shown in the list's own window; a record opened in a new window ignored it, as it did in Foundation 5. It is now carried across. If you set it for a table whose records open in their own windows, New now offers another blank record after each save, until Cancel.

The list window keeps up with records saved elsewhere. A record added in the list's own window now joins the list (it was saved but not shown). A record saved in its own window is added and selected if it is new, and redrawn with your selection left alone if it was already listed. Rows edited through Edit on several selected records now redraw as each is saved.

The hook comparison has its own window, opened after the installer closes, in place of a panel inside it.

The preference editor's Boolean checkbox works.

Additive

  • The installer can create the On Startup and On Exit database methods. When your database lacks either, the installer shows a box, ticked, "Start Foundation when this database opens"; Install then creates each missing method with one line, calling Fnd_Shell_OnStartup or Fnd_Shell_OnExit. A database method you already have is never read or changed: add the line to it yourself. Untick the box to create nothing.
  • Fnd_List_SortList sorts a command dialog. Called from the Administration, Print or Special Functions hook with "asc" or "desc", it shows the commands by name; with "none", or without the call, they keep the order they were added in.
  • Fnd_Loc_FixLabelWidths accepts object names as well as pointers.
  • Foundation's development tools work in your database. The new Fnd_Dev module (the Foundation Developer's Toolkit) has six shared methods that work on the database that calls them: the compile-check watcher (Fnd_Dev_SchedStart, Fnd_Dev_SchedStop), a one-off syntax check (Fnd_Dev_CompilerCheck), the documentation writers (Fnd_Dev_WriteDocumentation, which takes an options object, and Fnd_Dev_WriteClassDocumentation) and Fnd_Dev_ResizeDesignWindows. Interpreted only. See chapter 11 of the Guide, In a database that uses Foundation.
  • Fnd_Gen_Assert checks an assumption and guards on it. It returns the condition it is given, so If (Fnd_Gen_Assert($customer_e#Null; "No customer")) both checks and protects the code that needs the customer. A false condition is recorded as a test failure during a test run, opens the debugger when Foundation runs interpreted, and is otherwise logged and shown as a notification through Fnd_Gen_BugAlert; it never stops an unattended run. See chapter 11 of the Guide, Assumption checks.
  • The installer compares your hook methods with Foundation's. A hook method already in your database is compared with every version of it Foundation has shipped in 6.0. One that is an unchanged earlier version can be replaced; one you have edited since can have Foundation's later changes applied to it, when they do not overlap yours, after a look at both. Each has a tick box, off by default, and nothing is written unless you tick it and choose Apply; the code it replaces is first saved in a folder named Foundation Backups in your database's folder. Changes that overlap yours are shown for you to copy by hand. Hooks written for Foundation 5 have no 6.0 version to start from, so they are listed for reference only, folded away. Before Foundation 6.0 a hook was written once and never compared.
  • New hook and host methods are generated invisible, in a new layout. The hook methods Foundation writes into a database now carry //MARK:- Your code and //MARK:- End of your code markers: the code between them is yours, and Foundation may update the rest in a later release. They open with a short description, the example code and any defaults Foundation sets, and they are shared and hidden from the method list like the host methods. Hooks already in your database are not changed.
  • Fnd_Dlg_CustomIcon accepts a full path in POSIX form (/Users/…/icon.png) as well as in system form.
  • The cs.fnd classes are documented as a first step. cs.fnd.text, cs.fnd.date, cs.fnd.pswd, cs.fnd.pref and cs.fnd.log each cover part of their module and show the direction Foundation's code is taking. The Fnd_<Module>_ methods remain the complete, supported interface, and more functions will follow in later releases.
  • Fnd_Hook_IO_OnValidate is a new hook. Foundation calls it, with the table and the form's name, before every save it makes from an input form. Code that must run before a record is saved can live there, in one place, in place of an On Validate branch in each form method. Fnd_Dev_ConvertOnValidate steps through your forms' On Validate code one case at a time and proposes the hook's entry for each; you can edit each proposal, nothing is written until you choose Apply, and what it replaces is first saved in Resources/Foundation/OnValidate-Backups. Interpreted only.
  • An input form can be shown with DIALOG, in place of MODIFY RECORD and ADD RECORD, which gives the form a Form object. It is off unless you turn it on, with Fnd_IO_UseDialog: for the whole database (Fnd_IO_UseDialog(True)), for one table (Fnd_IO_UseDialog(->[Table]; True)) or for one form (Fnd_IO_UseDialog(->[Table]; "Input"; True)). On Validate does not fire for a form shown this way, so anything a form does there must move to Fnd_Hook_IO_OnValidate first. Foundation checks: at the database and table levels, a form whose method still handles On Validate stays on MODIFY RECORD; only naming the form overrules that. Not yet tried with mandatory fields or entry filters.
  • Fnd_Dev_SanityCheck looks for what the compiler cannot see: form files that do not match 4D's form schema, event names 4D will not recognise, and forms not ready for the DIALOG route. Interpreted only.
  • Fnd_IO_DisplayRecord also takes its parameters as one object: Fnd_IO_DisplayRecord(New object("tableNumber"; Table(->[Contacts]); "recordNumber"; $n)). The table goes in as a number. Calls that pass a table pointer are unchanged.

Known issues

  • Dark mode, what is left (FND-112, FND-115). The list window, its View Options palette and the alert icons now suit the dark colour scheme (see Behavioural). Two things do not: the toolbar strip stays light, with dark labels and a black status line, in both schemes; and a row colour chosen in View Options is fixed, so a light colour picked in the light scheme leaves white text on a pale row in the dark one. Option-click the swatch to return it to automatic.
  • Replacing a superseded form is done by hand (FND-108), as in beta.4.

6.0.0-beta.4 (private beta, 22 November 2026)

The last beta. Run Fnd_Shell_Installer once in each host, interpreted, after installing it: this release has more for the installer to do than any before it.

Breaking

Nothing. No shared method was removed or had its parameters narrowed.

Behavioural

The installer supplies the host forms and their pictures (FND-106). The five forms Foundation's windows are built on (Fnd_Tlbr_Toolbar, Fnd_IO_InputForm, Fnd_IO_InputTemplate, Fnd_IO_OutputTemplate and Fnd_Out) are copied into the host's Forms folder when they are missing, and the pictures they use into one folder, Resources/Foundation, with a README.txt listing each picture and the form that uses it. Copying them by hand from Foundation Product Sales is no longer needed. A form or picture already in the host is never replaced. A missing form opens the installer at start-up, once a session, in an interpreted host; Cancel leaves it out for that session. Project-mode hosts only. What to do: a new host, choose Install. An existing host, see the next entry.

Hosts from an earlier beta: let the installer re-add the Foundation forms. Recommended, not required. A host installed from beta.1 to beta.3 keeps the forms it was given, and they still work, but it misses what has changed in them since: the tidied toolbar form, buttons that no longer need process variables, the Retina and dark navigation pictures, and the single Resources/Foundation folder. What to do:

  • The installer's page now ends with "Installed earlier, since changed", marking each such form superseded (yours is as Foundation supplied it) or edited (you have changed it).
  • Delete the folder of each superseded form from the database's Forms folder. At the next interpreted start-up Foundation notices it is missing and opens the installer; Install copies the current form and its pictures in.
  • Keep a form marked edited: deleting it loses your changes. It goes on working with the pictures it already has. To give its record-navigation buttons the new pictures, copy the twelve Fnd_IO_*Rec@2x.png, _dark.png and @2x_dark.png files from Resources/Foundation to wherever the form looks for the originals (Resources/Images in an earlier beta).
  • Afterwards the old picture copies (Resources/Fnd_Tlbr_Images, and the Fnd_IO_*Rec files in Resources/Images) may be deleted, once no form of yours still names them.
  • Forms of your own that inherit from a Foundation form need no change.

Tables made by an earlier Foundation are upgraded by the installer (FND-88). The tables Foundation creates (Fnd_Pref, Fnd_List, Fnd_SqNo, and Fnd_Log and Fnd_Reg where used) are now created with a primary key and included in the journal. One made by an earlier version may lack either; without a key 4D keeps a table out of the journal and out of ds. The installer lists each such table under "Table upgrades", saying which it needs, and on Install adds the key and enables journaling. A row whose ID is empty, or the same as an earlier row's, is given a new ID; no other row is changed. A table that cannot be upgraded is named in the closing alert and left as it was. This is never done at start-up. What to do: back up, run Fnd_Shell_Installer interpreted, choose Install.

A new release announces itself, once (FND-108). The first time a host is opened interpreted after a new Foundation release, a dialog offers Review now, Skip this release and Never ask. Review now opens the installer page, which leads with what has changed in the release, then anything missing, then the forms and pictures that differ. Nothing is installed unless Install is chosen there. The answer is kept per machine in Settings/Foundation.json beside the host's Project folder. A compiled host, a server and a remote client never see it, so end users never do. What to do: nothing.

List configuration has moved to Resources/Foundation/Fnd_Out. What a developer saves from the list window (offered fields, application layouts) is now written to Resources/Foundation/Fnd_Out/<Table>.json. Files in the old Resources/Fnd_Out are still read until that table is next saved, and are never moved or deleted by Foundation. What to do: nothing; once each table has been saved, or its file moved by hand, the old folder may be deleted. Keep the new files under version control with the database.

Save in the list's Layout menu saves whatever layout is in force. It used to refuse Standard, application and shared layouts. Now a personal layout is replaced; a shared layout is republished, for a user allowed to publish; an application layout, or Standard itself, is written to the table's configuration file from an interpreted host. A compiled host refuses those two and points to Save As…. A saved Standard is what Standard means for that table from then on; Delete Application Layout, chosen while on Standard, removes it. What to do: nothing.

A list refreshes when its window comes to the front. An open list kept showing a record as it was when the list was drawn; a change saved in another window, or by another user, appeared only after a manual refresh. What to do: nothing.

A new host's lists open in the list window by default. The Fnd_Hook_IO_DisplayTable the installer writes now turns the Fnd_Out list on, so a new host needs no Output form per table. A hook already in a host is not touched. What to do: nothing.

The Sort dialog sorts, and remembers. With the list window active, beta.3's Sort dialog ran the sort and then put the old order back; it also never reopened on the field and direction last used. Both are fixed. What to do: nothing.

Dark mode. Navigation palette text left on automatic is now black or white, whichever reads against the button's background; a colour the host sets is used unchanged. The calendar popup is readable in a dark host, and its empty days no longer show 0 (they did in beta.1 to beta.3). The record-navigation buttons and the calendar's arrows have Retina and dark pictures, which 4D chooses by itself. Other dark-mode faults remain: see Known issues. What to do: nothing.

Process variables replaced in Sort, Find and Modify Records (FND-103). In Fnd_Sort, Fnd_Find and Fnd_Rec, process variables and arrays have been replaced in two ways. What a dialog displays is now bound to the 4D Form object. What the module remembers between calls is held in one object per process, Fnd, with a property for each module:

Fnd.Rec.EditorButtonLabel_t   // "By Formula..."
Fnd.Sort.Direction_i

Fnd_Bttn, Fnd_Dlg, Fnd_IO, Fnd_Menu and Fnd_Wnd were done the same way in earlier betas. Fnd is Foundation's own; a host should go on using the shared methods, which keep their names, parameters and behaviour. What to do: nothing.

Fnd_IO_InputForm's buttons no longer use process variables (FND-103). The form the installer supplies no longer binds its eight buttons (Save, Cancel, Close, Esc and the four record-navigation buttons) to variables. A form already in a host keeps its variables and goes on working. What to do: nothing; or, to match, clear the Variable or Expression of each of the eight buttons and remove the eight C_LONGINT(Fnd_IO_…Button_i) lines from the host's own compiler method. Leave the object names as they are.

Logging. Fnd_Log_CreateTable no longer overwrites the clipboard, as it did in the first three betas. Entries logged between Fnd_Log_Shutdown and the last log writer ending are now dropped rather than restarting the writers; logging resumes by itself afterwards. What to check: a host that logs straight after calling Fnd_Log_Shutdown should expect to lose those lines.

Additive

  • Fnd_Find_Engine takes the search option as an optional second parameter (FND-103): 1 all records, 2 the current selection, 3 add to it, 4 omit from it. It hands the option to a custom search method as that method's fourth parameter. Foundation's own Find passes it. A host that calls Fnd_Find_Engine itself with a custom search method must pass it too, or the custom method receives 0.
  • The installer has a Done button. When nothing is missing its page shows a single Done in place of Install and Cancel.

Known issues

  • Dark mode is unfinished in the list window (FND-112). In a dark host the list's alternate rows, the toolbar's status line and the labels of the View Options palette are hard to read. Cosmetic; a light host is unaffected.
  • Replacing a superseded form is by hand, as described above. An updater is planned after 6.0 (FND-108).
  • Not yet measured in client-server: whether the list window fetches only the columns it shows (FND-73). It works correctly in client-server; this is about efficiency only.

6.0.0-beta.3 (private beta, 15 November 2026)

Breaking

Ten shared methods are gone (FND-35). Six had been flagged _DeleteMe since August or earlier; four lost their purpose when the interprocess variables they served were removed. A host that still calls one no longer compiles.

Fnd_Gen_DummyMethod, Fnd_Nav_DummyMethod, Fnd_Pref_DummyMethod, Fnd_Rec_ModifyErrorHandlerFnd_Gen_SilentError (same empty body; for ON ERR CALL and the close-box parameter of Open window)

Fnd_Out_ORDARelatedFieldnothing; it had no callers

What to do: search the host for each name and replace it as shown. A compiled host that named one of the retired Compiler_Fnd_Data, Compiler_Fnd_Date, Compiler_Fnd_Ext or Compiler_Fnd_Wnd entries in its own typing was declaring Foundation's variables, which it never should have; remove the entry.

Behavioural

Local and server preference names ignore case again, as in Foundation 5 (FND-104). Betas 1 and 2 matched them exactly, so Fnd_Pref_GetText("mainPrinter") missed a preference saved as MainPrinter. A preferences file that picked up two spellings of one name is merged on load, the non-empty value winning. What to do: nothing.

Foundation asks before it adds anything to a host (FND-105). Nothing appears in the database by itself any more. In an interpreted host, the first Foundation call that finds something missing opens the installer dialog, which lists what it will add: three tables (Fnd_Pref, Fnd_List, Fnd_SqNo), the 30 Fnd_Hook_ methods, the 11 Fnd_Host_ methods and Compiler_Fnd_HookAndHost, all in one request. Cancel adds nothing. A compiled host is never changed. A host that already has them sees no dialog. What to do: add the component, open the database interpreted, run Fnd_Shell_Installer (or accept the dialog), choose Install, then restart the database: the restart is needed both for the new tables and for the new methods to compile.

The input form's Save and Cancel buttons take Foundation's localized title (FND-103). Fnd_IO_InputDrawButtons runs on the host's copy of Fnd_IO_InputForm. It used to address the two buttons through a pointer to a variable the host's form object is not bound to, so the title was never set and the buttons kept whatever text the host's form gave them. It now addresses them by object name: the title is the SaveButton or CancelButton string of Fnd_IO in the current language, and the width is measured from it. What to do: nothing, unless the host typed its own text on those two buttons, which is now replaced. The object names Fnd_IO_OKButton_i and Fnd_IO_CancelButton_i must stay as they are.

Fnd_Tlbr_Button_Position finds the button on the host's toolbar (FND-103). It also went through a pointer to a variable the host cannot see. Nothing in Foundation calls it. What to check: a host that calls it should check what it now gets back.

Additive

  • Fnd_Shell_Installer is new and shared. A developer can run it at any time to see what Foundation would add to the database, or to confirm that nothing is missing.
  • Fnd_Dlg_SetClickToCopy(enable) (FND-95) is new and shared. After Fnd_Dlg_SetClickToCopy(True), a click on the text of an alert, confirm or request dialog puts it on the pasteboard: the heading, a blank line, then the details (the heading alone when there are no details). It is off until called, and the setting is shared by every process, so one call at startup is enough. A host that does nothing sees no change.

6.0.0-beta.2 (private beta, 8 November 2026)

Breaking

None. No shared method was removed or made private, and every call that compiled against beta.1 still compiles.

Behavioural

The Window menu lists windows, not processes (FND-54). Foundation now keeps one registry of windows, each entry holding the window reference and its process. A process with several windows gets one Window-menu item per window that asks for one, and choosing an item raises that window rather than every window of the process.

Fnd_Menu_Window_Add works on the current form window, so call it after the window is open. It also decides which window is the process's prime: the one whose closing lets the process method carry on, and which Close All closes last. Left out, a window added from process-method level is taken to be prime and one added from inside a running form is not. Outside a form it falls back to the process's frontmost window. What to do: nothing for the usual On Load call. Pass False as the new second parameter for a window opened with DIALOG(...; *) from process-method level, because the process carries on after it; "" as the first parameter keeps the window's title.

Fnd_Menu_Window_Remove takes a window reference or a process number. A number that is a registered window removes that window; any other number removes all of that process's windows. The window stays open, and stays in Close All. With no parameter it removes the current process's most recently added window.

Close All reaches every closeable window of a process, not only its frontmost window. Each window is asked once, its siblings before the process's prime window, which is asked only when they have gone. A form that handles On Outside Call still decides for itself, with Fnd_Wnd_CloseNow and Fnd_Wnd_CancelCloseAll; Foundation brings that window to the front first, because the outside call reaches only the frontmost one. What to check: a closeable window whose form neither handles On Outside Call nor has an onClose method used to ignore Close All, and is now closed with no chance to refuse.

Fnd_Wnd_SendCloseRequests marks a window, not a process. Called in a process with no window yet, as at the top of a process method, it marks the next window that process opens through Fnd_Wnd_OpenWindow or Fnd_Wnd_OpenFormWindow, and only that one. Otherwise it marks the frontmost visible window. Fnd_Wnd_SendCloseRequests(process) now works for another process, provided it has a visible window: it used to record the caller's process name, so the entry was dropped as dead. A host that passes a number, and was relying on nothing happening, should check that call.

Fnd_Wnd_MoveOnScreen reads the screens each time, so rearranging monitors while the application runs is noticed, and its multi-screen handling now runs in Windows SDI mode.

Fnd_Out_AddToSelection no longer raises error 1600 when called from outside the list's table context; it does nothing when there is no record to add.

Fnd_Date_DateAndTimeToISO is correct for early dates on 4D 21 R. On 21 R4 and 21 R5, 4D's String(date; ISO date) returns 0000-00-00T00:00:00 for every date up to and including 1 January 1900, and this method used to pass that on. It now builds the text itself. Its output on every other date and version is unchanged. What to do: nothing for Foundation's method; code of your own that calls String with ISO date on such dates has the same fault on 21 R.

Additive

  • The Fnd_Out search box (FND-81) is new and optional. To use it, add a subform object named exactly Fnd_Out_Search, with detail form Fnd_Out_Search, to the host's Fnd_Out form once, and declare each table's searchable fields in Fnd_Hook_Out_SearchFields with Fnd_Out_AddSearchField. Foundation generates both hooks (Fnd_Hook_Out_SearchFields and the optional Fnd_Hook_Out_Search) the first time Fnd_Out runs. A table with no declared fields hides the box; a host without the object is unaffected. Draw the object anywhere in the toolbar band, about 192 × 26: Foundation places it when the list opens and on every resize, 10 pixels from the window's right edge, centred in the band and never over the toolbar buttons, and hides it when the window is too narrow to fit it. The empty box shows the searched fields' names in grey, and its tip lists them all. A name is the field's virtual field name unless Fnd_Out_AddSearchField's optional third parameter (or fo_title in the object form, beside fo_field and fo_operator) gives another. Fnd_Out_SearchHint(hint; tooltip), called in the hook, replaces the hint or the tip for that table, and Fnd_Out_SearchHelp returns the generated list for a tip of your own.
  • Fonts in the list window (FND-82). Users can choose the list's font in View Options and a single column's font in Advanced; both are saved with the list's layout. A saved layout holds a font only when the user chose one, so Fnd_Out_Default(Fnd_Out_FontName; …) still sets the font everywhere else.
  • The window registry is published (FND-54): Fnd_Wnd_Register, Fnd_Wnd_Unregister, Fnd_Wnd_Windows and Fnd_Wnd_CloseWindow. Windows opened by Fnd_Wnd_OpenWindow are registered automatically and stay out of the Window menu and Close All until they opt in. A window opened with 4D's own Open window, or a palette from Fnd_Wnd_OpenFormWindow, is not registered until you register it.
  • The About box credits the incorporated components and further contributors.

6.0.0-beta.1 (private beta, 1 November 2026)

First release under the new versioning scheme. The component is built for four targets from one commit, all carrying the same version: 20L (4D 20 LTS), 20R (4D 20 R), 21L (4D 21 LTS) and 21R (4D 21 R). The floor is 4D 20 LTS; 4D 19 is no longer supported. Foundation is released under the MIT licence.

Breaking

Foundation's own licensing is gone. Fnd_Gen_Reg_*, Fnd_Gen_RemoveActivationCode, their two forms and Resources/Fnd_License.xml are removed (FND-61, FND-62). A host that called Fnd_Gen_RemoveActivationCode, or had a menu item for it, must remove the call. Fnd_Reg, which licenses the host's application, is unaffected.

cs.fnd.wnd is no longer published. The unfinished class is now _wnd_sketch. A host that referred to cs.fnd.wnd must remove the reference; nothing worked through it (FND-44).

The standalone Logging component is removed, and Foundation records through Fnd_Log (FND-96). A host that installed Logging.4dbase only for Foundation's sake can remove it; a host that calls the Logging component's own methods keeps its copy.

German's language code is DE, not GR. Fnd_Loc_LanguageCode returns DE. A host with its own _GR lists for German renames them _DE.

Behavioural

Fnd_Reg offers to create [Fnd_Reg]. A host that uses Fnd_Reg without a [Fnd_Reg] table no longer aborts. In an interpreted host during development, Fnd_Reg asks whether to create the table, then asks for a restart; a compiled host gets a report. Either way Fnd_Reg stays inactive for the session. Hosts with the table already in place need do nothing (FND-85). Fnd_Reg_Init is not part of the published API: do not call it from a host.

Fnd_Reg registration fixes (FND-87, FND-90, FND-93, FND-94). Duplicate records are resolved rather than aborting; days remaining honour a demo period set before the demo starts; the registration dialog is not shown once registered; and a tampered record reports Expired on the call that detects it. Hosts need do nothing.

Fnd_Loc names a missing Fnd_Host_ListToArray. A host without the hook now gets one report naming it, instead of empty strings (FND-39). Hosts that have the hook see no change.

Fnd_Dlg keeps its state in objects. The module's process and interprocess variables (Fnd_Dlg_Text1_t, <>Fnd_Dlg_ProgFrom_i and the rest) are gone, replaced by Fnd.Dlg and Storage.Fnd.Dlg. Component variables were never visible to a host, so the public methods behave as before, with one exception: Fnd_Dlg_SetIcon(0), or any value other than Fnd_Dlg_WarnIcon and Fnd_Dlg_StopIcon, now resets the next alert to the Note icon instead of leaving the previous alert's icon in place. A host that wants the old leak has none.

Development history in method headers is one line. Every modification line dated 2026-08-01 to 2026-11-01 reads "Prepare Foundation 6 release"; earlier lines are unchanged. Nothing to do; it is why a diff against Foundation 5 headers looks shorter than the code change.

Additive

  • Fnd_Reg_CreateTable is new and shared, for creating the [Fnd_Reg] table by hand in an interpreted host.
  • Fnd_Art_VersionHistory is new. A host can pass release notes (styled text, newest first) to show on the About box's About tab; without them the area is hidden. The generic About box is now tabbed (About / Foundation / Foundation Licence), resizable, and credits Dave Batton and Walt Nelson (FND-59).
  • Fnd_VS_zProbeHostLists is published, as a diagnostic: it reports which route to a host's choice lists works in that database.

Also in 6.0.0-beta.1 — the August 2026 modernisation of Fnd_Text and Fnd_Data

The Fnd_Text and Fnd_Data modules were modernised: hand-written MD5 and Base64 replaced by the 4D commands that now do the same work, and module state moved out of interprocess variables into Storage.

Breaking

63 methods are no longer callable from a host. They carried "shared":true and no longer do — 33 Compiler_Fnd_* methods and 30 Fnd_*_Init methods, including Fnd_Init itself. The shared surface went from 698 to 633.

This is deliberate and settled (Wayne, 2026-08-13). Neither family is part of the published API: Compiler_Fnd_* methods are declaration scaffolding a host has no reason to name, and Fnd_*_Init is called by every public method in its module on entry — and has been since 2004 — so a host calling one was calling it a second time for no effect.

Note that the change is not merely documentary. The %attributes flag is what 4D checks when a host resolves a name, so the same edit that corrected the claim also withdrew the method.

A host that calls any Fnd_*_Init directly will therefore fail at that call. This is not hypothetical: Foundation-Product-Sales, the reference host, calls Fnd_Wnd_Init from a form object method (Forms/_Matrix_Testing/ObjectMethods/Button.4dm, line 1).

What to do. Nothing, if the host only calls public Fnd_<Module>_<Verb> methods — every one of those kept its flag, verified method by method. If the host calls an Init or a Compiler_Fnd_* method directly, delete the call rather than replacing it; there is nothing to replace it with, and nothing was relying on it.

Three MD5 helpers were removed, having been shared:true: Fnd_Text_TextToMD5_Bits32Add, Fnd_Text_TextToMD5_Bits32Left, Fnd_Text_TextToMD5_Calc. They were the internals of the hand-written digest and are meaningless outside it. A host calling them was reaching into the implementation; use Fnd_Text_TextToMD5.

Interprocess and process variables are gone, not renamed. A host reading any of these by name finds nothing:

<>Fnd_Data_Initialized_bStorage.Fnd.Data.Initialized

<>Fnd_Data_UserBypassKey_iStorage.Fnd.Data.bypassKey

Two flags were re-spelled to the US spelling the rest of the component uses. <>Fnd_Tbl_Initialised_b is now <>Fnd_Tbl_Initialized_b, and the per-process Fnd.List.Initialised is now Fnd.List.Initialized. This matters beyond tidiness: Fnd_Gen_Reset builds the flag name as a formula and swallows the error when it misses, so a module spelling its own flag the British way was silently never reset.

Behavioural

Fnd_Data_FormatWebURL now defaults to https. A URL arriving with no scheme was given http://; it is now given https://. Trailing-slash normalisation, which previously matched only http://, now applies to both. A URL that already carries a scheme is untouched, as before.

Fnd_Data_FormatWebURL("example.com")                    // https://example.com/
Fnd_Data_FormatWebURL("example.com"; {scheme: "http"})  // http://example.com/

Stored values are not migrated. A host that formatted URLs on entry has http:// in its data and will produce https:// from now on, so the same input will not match a stored value. Pass {scheme: "http"} to keep the old behaviour at a particular call site.

Fnd_Text_EncodeBase64Blob no longer prefixes a carriage return. The old encoder wrote a line break before the first character and sized the blob to allow for it, so Fnd_Text_TextToBase64("Man") returned five characters where four were asked for. It now returns TWFu.

This reaches Fnd_Text_TextToBase64 too, and it changes the output every existing caller has been receiving. Anything that stored, transmitted or compared those values holds strings with a leading carriage return that fresh encodings will no longer match. The 76-character wrapping is unchanged — BASE64 ENCODE does not wrap, so the wrapper still does.

Verified unchanged

Recorded because they are the changes most likely to be feared:

  • MD5 digests are identical. Fnd_Text_TextToMD5 delegates to Generate digest, and the default charset stays ISO-8859-1 — what the hand-written digest always used — so stored digests still match. Test_Fnd_Text asserts the RFC 1321 vectors and the accented-text digest against the default.
  • Base64 decoding still tolerates whitespace. The old decoder ignored line breaks incidentally; BASE64 DECODE is stricter, so Fnd_Text_DecodeBase64Blob now strips CR, LF, tab and space before calling it. Same result, deliberately.
  • Fnd_Text_Wrap output is unchanged. Rewritten to walk an index rather than delete the front of the text on each pass — a performance change only, pinned by boundary tests including exactly-at-limit, over-limit with no space, and an embedded carriage return.

Additive

  • cs.fnd.text — the Fnd_Text module through the class store: cs.fnd.text.new().capitalize("hello world"). Every function delegates to the method of the same behaviour, so the two routes cannot diverge. 4D 20 LTS has no singletons, hence new().
  • Fnd_Text_MD5Encoding — reads the default MD5 charset, or sets it for every later call.
  • New trailing optional parameters, all backwards compatible: Fnd_Data_FormatWebURL and Fnd_Data_FormatText take an options object; Fnd_Data_EmailAddressError takes a pointer for the description; Fnd_Text_TextToMD5 takes a charset.
  • Fnd_Data_FormatPhone and Fnd_Data_FormatPostalCode widened their style parameter from Integer to Variant and dispatch on Value type, so an options object is accepted where the legacy style constant still works.
  • Fnd_Data_ParseName now also returns an object, in addition to the output pointers it has always filled.
